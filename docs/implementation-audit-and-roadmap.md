# InvestIQ implementation audit and roadmap

Audit date: 2026-11-22. This is a live completion matrix, not a claim of production readiness. Phase 1 and Phase 2 remain **incomplete** because the definition of done includes real authentication/database end-to-end tests and production/security work that has not been performed. Do not use real sensitive data yet.

## Current architecture

- Frontend: `web/app/` plus `web/components/workspace.tsx`, Next.js, React, TypeScript, Tailwind and custom CSS; same-origin `/api/*` rewrite to the Python server. Not yet shadcn/ui, Recharts, full requested navigation, dark mode, CSV or verified accessible/browser-tested UI.
- Backend: `investiq/platform/api.py` is a FastAPI modular-monolith prototype, using psycopg and Pydantic; the external `/api/v1` prefix is mapped to internal `/v1`. `investiq/platform/planning.py` isolates decimal calculations. Existing evidence, prototypes and lab packages are separate domains. It is not SQLAlchemy and has no job queue or rate limiter.
- Database: migrations `20261122000100_evidence_infrastructure.sql`, `20261122000200_unified_platform.sql`, `20261122000300_savings_mission.sql` create evidence records and snapshots, user consent, financial snapshots, audits, forecasts, missions and contributions. These are not the entire target schema. Supabase Auth users own records through UUIDs and RLS; personal snapshots and mission records are append-only. New plans are separate records and contributions remain attached to the plan they were recorded against. A dedicated remote database has not been provisioned or migrated.
- Authentication: Supabase password-token API and server-side user validation; secure, HttpOnly, SameSite cookie. The token is not refreshed or revoked on logout. No signup, MFA enforcement, recovery or production auth/browser test exists. The API service must remain private and app/evidence schemas must not be exposed through PostgREST; direct authenticated SQL writes could forge evidence and audit events. Existing consent revocation blocks personal-finance reads and writes, not deletion. RLS does not substitute for a retention/deletion policy.
- Infrastructure: locked Python and npm dependencies, local setup and staging procedure in [the platform guide](unified-platform.md). Local Supabase CLI configuration and a Windows setup script are provided, but their complete Docker/Windows workflow has not been verified. No CI, production hosting, automatic backup/recovery, security assessment or real market feed has been configured. Node 22+ and Python 3.11 were used locally; no GPU is required. No remote project was modified.

## Incremental work and validation

The current increment adds `investiq/platform/planning.py`, `supabase/migrations/20261122000300_savings_mission.sql`, `tests/platform/test_planning.py` and this document; modifies `investiq/platform/api.py`, `web/components/workspace.tsx`, `tests/platform/test_api.py`, README and the setup guide. Existing research prototypes were retained. Existing personal arithmetic responses now return decimal strings rather than floats; statistical TFSF/ECCR prototypes use floating-point numerical algorithms and are not monetary ledgers.

The new mission defaults are an **editable example**, not claimed as personal data: ₹23,000 income, ₹17,500 planned savings, ₹3,500 personal expenses, ₹1,000 learning, ₹1,000 emergency, ₹4,20,000 target over 24 months. Benefits are unchecked until the user explicitly confirms them. No example record is persisted automatically. Decimal arithmetic is used by the mission and calculator functions; returned values are decimal strings and rounded to two places at output (half up). Savings = contribution × months. SIP assumes equal end-of-month contributions and nominal constant annual rate divided by 12; compound interest uses monthly compounding. Zero-rate SIP is handled separately. These are hypothetical illustrations, not promises, and omit taxes, fees, inflation and changing returns. Mission completion is actual recorded contributions / target; missed-month notices compare recorded contributions with planned contribution for completed calendar months only, including the starting calendar month even if the start date is mid-month. Calculation time is the current UTC date. More than 100% completion is possible. Plans are not linked to bank accounts and records can be duplicated by repeated submissions.

New external routes: `POST/GET /api/v1/goals`, `GET /api/v1/goals/progress`, `POST /api/v1/savings/contributions`, and `POST /api/v1/calculators/{savings,sip,compound-interest}`. Mission and contribution routes require authenticated user and consent; stateless calculators require authentication but do not persist inputs. Current mission is the most recently created plan. Calculators and mission record actions are not external AI actions; contribution/mission creation inserts application audit events.

Latest local checks: **61 tests passed** using the explicitly disposable PGlite socket database, including 3 planning arithmetic tests and selected API consent, mission and isolation workflows. These tests override authentication and reuse one database connection; they are not real Supabase/Postgres, browser or multi-user concurrency tests. The preceding frontend typecheck and production build passed; `npm audit --audit-level=high` reported zero vulnerabilities. The local Supabase config was parsed and the CLI version checked, but neither Docker nor Windows is available in the sandbox; the actual stack and PowerShell script remain untested. Warnings: MLflow/Pydantic and Starlette deprecations. No test dataset was used for model selection in this increment.

## Execution sequence

1. Complete foundation: dedicated staging Supabase project, minimum-privilege access, trusted audit architecture, robust session lifecycle, rate limits, secret scanning, consent and deletion/retention design, real RLS and auth end-to-end tests. Avoid modifying unrelated connected projects.
2. Complete personal finance: normalized income/expense/employment and goals; corrected snapshots with history; all specified decimal calculators and ledger-level tests; configurable milestones, scenario histories and visualizations driven solely by user data; CSV validation/import/export. Run authenticated browser E2E on real staging, accessibility, performance, backup and recovery tests. Document assumptions, formulas and dates.
3. Only then build licensed investment ingestion, point-in-time instruments, corporate actions, portfolios and deterministic indicators with numerical reference tests.
4. Extend temporal financial state estimation and independently validate against robust baselines. Persist source, confidence and validation metadata; never conflate numerical model variance with guaranteed coverage.
5. Add bounded agents and evidence verification with independent hypotheses, source checks and disagreement retention. No privileged direct mutations. Test adversarial failure and abstention.
6. Add reproducible counterfactual scenarios, uncertainty and sensitivity, including explicit assumptions and snapshots. Use Monte Carlo only when assumptions are justified.
7. Build registries, locked train/validation/test procedures, forecast scoring and scientific reporting; no claims of novelty or improvement without literature-based validation.
8. Independently review security, reliability, regulatory scope, performance, recovery, and complete end-to-end tests before any production launch.
